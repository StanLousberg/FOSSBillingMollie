# One-time payments

MolliePayments implements one-time Mollie Checkout through FOSSBilling's native invoice gateway interface. It is a development integration, **not a production-ready release**. Automated tests use fake Mollie responses and disposable accounting databases. A real Mollie Test payment and public webhook must also be verified before deployment.

Customer creation/reuse, explicit first-payment onboarding and provider mandate verification are implemented as described below. Automatic recurring collection, Mollie Subscriptions, refunds and chargeback accounting are not implemented. Subscription capability remains disabled.

## Enable and validate

Follow [INSTALLATION.md](INSTALLATION.md) for dependencies, links, schema upgrades and saved credentials. Keep the existing public HTTPS system URL reachable; all callbacks use that native host configuration. Use only disposable customers, orders and issued unpaid invoices in Test mode.

Select MolliePayments in the invoice's normal gateway list. Complete Hosted Checkout and verify the provider state, invoice, transaction amount, account balance, activation tasks and settlement guard. Redelivering a callback must not add financial entries. Commands, real payment evidence and remaining gaps are in [VALIDATION.md](VALIDATION.md).

## Checkout and callbacks

The adapter delegates to `PaymentService`. It checks native invoice payment authorization, issued/unpaid state, client identity/currency, gateway type, enabled/one-time flags and accepted currency. It obtains the full host total including tax and compares integer minor units after quantizing the host's float-valued API once. Previously charged items or invoice allocations are rejected, not subtracted. No browser amount, status, environment or callback URL is accepted.

MolliePayments is an adapter, not a billing system. FOSSBilling owns invoices, account credit, pricing, tax, the ledger, transaction processing and service activation. Checkout never allocates, reserves, deducts or releases existing credit. A €25 invoice costs €25 through Mollie whether the customer has €0, €10, €25 or €30 in credit. Customers may instead use the native account-credit action: €25 settles it; €30 leaves €5. Adding funds after creation never changes the saved provider amount.

The tested host's `getTotalWithTax()` returns the invoice total, not an authoritative outstanding balance. `tryPayWithCredits()` / `payInvoiceWithCredits()` support full credit payment; they do not provide a gateway-independent partial allocation API. Charged items, nonzero legacy invoice credit, prior invoice debits and nonzero/unknown processed receipts therefore block checkout for reconciliation. The adapter only detects these conditions through native repositories; it does not sum ledger rows or infer paid amounts. Client/invoice currencies must match, only two-decimal currencies are supported and Add Funds invoices are rejected.

The minimal settlement bridge calls native `Client::addFunds()` for the verified receipt and its matching invoice debit, then native `Invoice::markAsPaid(false, false, true)`. No allocation engine or balance calculation is involved. Calling `tryPayWithCredits()` inside the outer settlement transaction would run its events and provisioning before commit; calling `markAsPaid()` with per-item charging can disagree with invoice-level tax rounding. Until core exposes an atomic deferred settlement API, the bridge preserves native invoice-level rounding, post-commit events and the attempt guard. See [core proposals](FOSSBILLING_CORE_PROPOSALS.md).

A committed reservation stores the exact creation payload, expected amount/currency, invoice/client/gateway/environment, idempotency key and a non-reversible credential binding. It contains no API keys, bank details or card data. A unique nullable active-invoice slot covers all MolliePayments gateway instances and environments. A bounded lease serializes checkout network calls; database uniqueness and provider idempotency protect recovery if a worker dies or outlives the lease. No database lock is held across a Mollie request.

The typed SDK v4 `CreatePaymentRequest` uses `Money` and `sequenceType: oneoff`, without a method restriction or `testmode` parameter. The selected saved API key determines the environment. The return uses the host's session-free `/invoice/payment-return` document before navigating to the invoice. This preserves the existing session when the browser withholds a Strict SameSite cookie on the cross-site return. No session tokens or relaxed cookie settings are used, and invoice authorization still runs normally. The invoice page displays the verified state. The Mollie description uses the native FOSSBilling payment title, including its series, padded invoice number and single-line item title, limited to Mollie's 255-character maximum. The webhook is the native `ipn.php?gateway_id=…&invoice_id=…&attempt_id=…` URL. Mollie posts a form field `id=tr_…`; callback values are routing hints only.

The callback resolves a stored attempt, fetches the actual payment through the authenticated SDK, and verifies the payment ID, metadata, invoice, client, gateway, environment, sequence, amount and currency. The native host transaction must refer to the same invoice and gateway. Only `paid` with a confirmed paid timestamp can settle. Changed invoice balance, missing ownership, refunds or chargebacks stop settlement with an actionable reconciliation error.

Settlement uses the host's existing transaction claim; the adapter never reclaims it. Under an invoice lock, it locks and refreshes the attempt and transaction, records the verified payment credit and matching invoice debit using `Client::addFunds()`, marks the invoice paid through `Invoice::markAsPaid()` without charging items again and writes transaction details and the attempt settlement guard in one database transaction. A duplicate delivery can have a separate audit transaction but moves zero money. Payment events run after commit; native cron handles pending item tasks. If the invoice was paid independently, received Mollie money remains recorded as a verified paid attempt requiring reconciliation, with no second credit or automatic reassignment.

Callback synchronization, settlement and non-paid transaction updates acquire the native invoice row lock and module attempt row lock before refreshing invoice state. An ORM reference avoids an initial invoice SELECT inside the transaction. This prevents a consistent-read snapshot from preceding the attempt lock while another worker updates mandate metadata. MariaDB with `innodb_snapshot_isolation=ON` can otherwise reject the later write with error 1020 even though the invoice is locked. The order remains invoice then attempt; accounting stays atomic, provider requests remain outside these locks and no automatic settlement retries are introduced.

## States and retries

| Mollie status | Behavior |
| --- | --- |
| `open` | Fetch and verify; reuse the same unexpired checkout URL when the invoice still matches. |
| `pending` | Leave unpaid; block a new payment and show processing. |
| `authorized` | Leave unpaid; authorization alone is not captured money. No manual capture workflow is implemented. |
| `paid` | Reconcile through the native claimed transaction path and settle once. |
| `failed`, `canceled`, `expired` | Release the active slot only after authenticated confirmation; selecting the gateway again creates a new attempt. |

An open payment with a changed invoice balance is never reused or automatically replaced. An expired checkout URL alone is not proof of a terminal payment: wait for authenticated terminal status. A stale pre-payment response cannot downgrade a verified paid attempt.

Mollie's idempotency cache lasts **one hour** and is bound to the credential. Unresolved creation retries use the same persisted payload/key only during a conservative **45-minute** window and with the same credential binding. After that, or after key rotation, creation stops for reconciliation. It never silently generates a new key. A delayed authenticated webhook can recover a missing Payment-ID from verified metadata. See [Mollie idempotency](https://docs.mollie.com/reference/api-idempotency).

Do not switch gateway environment or merchant profile while payments are active. Callbacks for a different saved environment are rejected. Restore the original environment to reconcile outstanding payments, then change configuration. A key rotation for an existing known Payment-ID is safe only if the replacement key can access the same original profile.

## Inspect and recover

From the host root:

```bash
ddev exec php src/modules/Molliepayments/bin/status.php /var/www/html/src
```

This prints the last ten operational attempt IDs and states, without credentials, raw payment responses, callback URLs or customer details. The tools in `bin/` are CLI-only.

For a known attempt and a provider Payment-ID identified in the Mollie dashboard, use the same native claimed reconciliation path:

```bash
ddev exec php src/modules/Molliepayments/bin/reconcile.php \
  /var/www/html/src ATTEMPT_ID tr_PAYMENT_ID
```

This is an authenticated provider fetch, not an override. It cannot settle mismatched data, another customer's invoice, an incorrect amount/currency or an independently paid/canceled invoice. It can bind the missing provider ID after a lost creation response. It creates/reuses a native transaction with sanitized errors. Alternatively, retry an errored callback through the native admin transaction **Process** action after correcting the cause.

- **API unavailable:** the attempt remains reserved. Provider failures return HTTP 503 through `ipn.php` so Mollie can retry. Received non-final transactions are also eligible for native cron reconciliation. Authenticated failed/canceled/expired deliveries are native `processed` audit rows with amount `0.00`, type `unknown`, the provider status and an explanatory note. They are not technical errors and native cron does not retry them.
- **Verification mismatch:** stop and compare invoice/client/gateway/environment and provider metadata. Do not force paid status or clear the active slot.
- **Verified paid / reconciliation required:** received money is preserved in the attempt and the failed native transaction. Check for an independent invoice payment, cancellation, allocation or currency change. Resolve through the host's accounting administration; this integration does not issue refunds or reassign money.
- **Creation unresolved:** search the Mollie dashboard using the invoice description and attempt metadata. Reconcile a matching payment with the CLI above. Do not delete the attempt or blindly retry after the idempotency window. If no payment can be established, investigate with the provider before any audited manual database repair.
- **Paid invoice but activation pending:** run/repair native FOSSBilling cron. Financial settlement does not run service-provisioning tasks under database locks.
- **Missing schema:** run the module migration and verify the module-scoped schema contract. No core patches or root Composer changes are supported.

Keep normal host authentication on the admin panel. Do not disable TLS verification. ## Legacy wallet transition

New installs contain no wallet fields. Additive module-scoped schema synchronization never drops existing columns, tables, attempt identities or ledger history. Runtime reads legacy columns only to reject historical split attempts; it never writes those fields. Existing `credit_amount`, `credit_state`, `invoice_balance`, reservation/release ledger references and records remain available for audit. Even orphaned reservation/release ledger history for an invoice blocks new checkout.

Before upgrading, disable new checkout, back up the database and inspect legacy columns if present. Inventory `credit_state = reserved`, all nonzero `credit_amount`, both ledger references and `client_balance` types `molliepayments_reserve` / `molliepayments_release`. Fetch the original payment in its original environment and compare invoice status, native debits, actual balance and settlement guard. Never release money based only on an attempt label.

Outstanding reservations need an administrator to determine whether funds were consumed, already released or still held. Resolve balances through audited native FOSSBilling administration with references to the preserved original entries, and reconcile/cancel the provider payment as appropriate. Do not delete financial history, clear active slots or drop columns to unblock checkout. There is deliberately no automatic release or destructive migration: provider finality and historical allocations cannot be inferred safely. Legacy split attempts remain blocked until individually reviewed; the generic reconciliation CLI cannot settle them as full invoices. Original non-wallet attempts remain compatible.

## Terminal transaction representation

`processed` means the callback was handled, not that money arrived. Terminal non-paid rows have zero amount and provider status `canceled`, `failed` or `expired`; details and invoice transaction history show that zero and the provider status. Host income reports derive revenue from paid/refunded invoices, while balance reports sum native balance entries. These callbacks create neither entries nor paid invoices, payment events or activation tasks. Duplicate callbacks remain financially inert. Genuine verification/processing exceptions remain native errors. Third-party reports counting all processed rows as successful payments need their own filtering; core lacks a dedicated unsuccessful-result outcome.

## Internal Customer integration (issue #7)

`Service::customers()->resolve(clientId, gatewayId, create: false, verify: false)` is the internal entry point for issue #8. It requires the host's authenticated `loggedin_client` identity to match `clientId`. It returns a provider ID or null; only `create: true` can initiate or retry creation. Customer resolution itself has no separate HTTP API or UI; the authenticated onboarding flow below invokes it. One-time checkout never invokes it. Onboarding validates invoice eligibility and explicit consent, and uses `verify: true` before attaching a first payment. Customer existence is not a mandate or recurring authorization.

`molliepayments_customer` stores one durable row per client/gateway/environment, with unique creation identity and provider mapping per gateway/environment. It stores identifiers, UTC DATETIME timestamps, a credential HMAC binding, the immutable creation request, worker lease and sanitized error state. New creation requests contain opaque metadata plus native-encrypted name/email details; there are no duplicate plaintext personal columns or bank/card information. `creating` preserves unresolved outcomes; `ready` allows local reuse without API requests; failed provider verification blocks cached reuse until a successful authenticated verification of the same Customer. Read-only resolution of an unresolved creation fails without API calls or state changes. An expired creation retains `recovery_required`; an observed profile mismatch records `profile_context_changed` and blocks cached reuse until verification succeeds again. A rejected attempt to replace a bound ID leaves the healthy mapping intact. No row is automatically deleted or replaced.

Customers are [organization-level resources](https://docs.mollie.com/reference/customers-api). API keys can query `profiles/me`, but `organizations/me` requires token permissions that this integration does not request. Consequently this phase conservatively binds each gateway/environment to the verified profile and original credential. It does not share Customers across gateway instances or profiles and does not pretend the profile is an organization ID. A credential change blocks even cached reuse; a profile mismatch blocks provider operations. Same-key cached reuse relies on Mollie's profile-bound API key contract. Rotated credentials and merchant changes require operator investigation; automatic credential rebinding is intentionally unsupported.

Creation commits the exact request snapshot, random reference and idempotency key before any Customer POST. The snapshot freezes `Client::getFullName()` and `Client::getEmail()` for retries even if the native profile changes. The full name is Unicode-whitespace-normalized, stripped of surrounding whitespace and capped at 255 characters; empty or control-containing names are omitted. Emails are trimmed, IDN domains encoded to Punycode, and only addresses accepted by native `EmailValidator::isEmailValid()` up to 254 bytes are sent. Missing/invalid optional values are omitted, never fabricated. Locale is omitted because this flow does not require overriding Mollie’s browser-language selection. Addresses, phone numbers and tax details are not sent. These fields are supported by the installed SDK v4 `CreateCustomerRequest` and [Create Customer API](https://docs.mollie.com/reference/create-customer).

Personal fields are encrypted with the host `crypt` service in the existing request JSON, bound to the creation mapping ID, and decrypted only for the original POST/replay. Opaque metadata stays readable for identity verification. Keep the native encryption secret available for unresolved retries. Unreadable/corrupt snapshots fail closed without a replacement POST. Existing metadata-only snapshots replay unchanged, and ready mappings are reused without replacement or silent updates. The provider [Update Customer API](https://docs.mollie.com/reference/update-customer) would permit enrichment, but an explicit verified update workflow is deliberately not included; normal lookup and mandate checks do not modify existing Customer details. A database uniqueness constraint resolves competing reservations, and a 180-second lease serializes network operations with fenced writes. An expired lease permits a safe replay only within 45 minutes of the original reservation and with the original credential/payload/key. Mollie's [idempotency contract](https://docs.mollie.com/reference/api-idempotency) caches POST responses for one hour and binds keys to credentials. The shorter local window leaves a safety margin. After it expires, only read-based recovery is allowed. API errors, malformed responses and timeouts preserve the row; they never authorize a fresh identifier. Do not wrap Customer operations in a host database transaction.

For an unresolved result, an operator with host CLI access must find the original Customer in Mollie's organization/environment by its `metadata.molliepayments_customer` reference. Use the provider list API or Dashboard as appropriate; do not match by email/name or assume absence from one page proves noncreation. Then run:

```bash
php module/Molliepayments/bin/recover-customer.php /absolute/path/to/FOSSBilling/src CLIENT_ID GATEWAY_ID MAPPING_ID CUSTOMER_ID
```

Recovery fetches the candidate using the saved gateway's current environment and original credential, checks profile, Customer ID, mode and exact opaque metadata, and binds it to the unchanged creation row. It records `ready` and updates the timestamp. It cannot replace a bound ID, cross clients/gateways/environments, clear state or issue a POST. Preserve operational evidence with the mapping ID and timestamps in the operator's audit record; do not include credentials or personal records. If the original outcome cannot be established, or the original credential is unavailable, the mapping remains blocked. There is no automated reset or credential-rotation recovery in this phase.

To repeat the real Customer API verification (completed on 2026-11-05): in a disposable Test-mode host only, invoke the internal service with a real authenticated disposable client from a local harness, explicitly opt into creation, and confirm one Customer with the opaque reference. Repeat resolution and explicit verification; confirm the same ID, test-mode resource and no second Customer. Exercise recovery with that same mapping/ID and verify a wrong reference is rejected. Confirm ordinary one-time checkout/settlement creates no Customer. Never put the key or raw provider responses in the harness, repository, screenshots or logs. CI tests fake Mollie; separate real Test API validation evidence is recorded in [VALIDATION.md](VALIDATION.md#issue-7-review-and-real-test-api-validation--2026-11-05). Neither establishes production readiness.


## First-payment onboarding (issue #8)

After upgrading the module schema, a logged-in customer can open:

```text
https://YOUR-FOSSBILLING-HOST/molliepayments/onboarding/INVOICE_ID
```

The native invoice `getHtml()` route automatically presents this page to an authenticated invoice owner when all invoice items are `InvoiceItem::TYPE_ORDER` references to the **same** existing order owned by that client. The order must have status `pending_setup` or `active`, a valid native `Period`, matching invoice-item periods, and no `cancel_at_period_end=1` metadata. This covers initial and renewal invoices without depending on expiry dates or fixed renewal prices. FOSSBilling's `Invoice\ServiceSubscription::isSubscribable()` answers whether a gateway can repeat a fixed invoice total, including discount/renewal-price restrictions; it is not the recurring-order classifier. Cart checkout issues native order invoices; `Invoice\Service::processInvoice()` invokes the adapter's `getHtml()` even with `supports_subscriptions=false`.

The shared `RecurringEligibility` check also guards the page, first-payment API, locked consent reservation, payment resume and mandate readiness. Standalone/custom/deposit lines, missing or foreign orders, canceled/suspended/failed orders, mismatched periods, mixed recurring/one-time items and multiple distinct recurring orders cannot grant authorization. Their normal payment flow remains `oneoff`, subject to existing checkout limitations (in particular, Add Funds invoices remain unsupported). This conservative policy also excludes custom discount/setup lines; it does not attempt to reconstruct billing intent from totals. Several lines for the same recurring order and period are permitted. No client-supplied recurring/period/order/gateway flag grants eligibility.

The unchecked checkbox authorizes only renewal invoices of the displayed order. **Authorize and start first payment** creates `first` with a verified Customer. **Pay once without future authorization** creates `oneoff` without a Customer or consent. Hash-only access preserves native one-time checkout and cannot grant consent; the separate onboarding route requires native client login. Exactly one configured MolliePayments gateway is required for the choice screen. Existing attempts are never converted: the page offers GET-based **Continue existing payment** for a known open payment, or status verification/support instructions. Resume cannot reserve or create a payment. Paid and pending pages hide new-payment forms. UI submission disables all actions together, and after a failed/lost response requires reloading before another choice. No core/theme injection or extra setup invoice is introduced.

The native client controller and `client/molliepayments/onboarding_start` API use the real client identity, invoice payment authorization, POST and the native session CSRF nonce. The module checks the original request because the host dispatcher removes `CSRFToken` from action parameters. This check remains required even if general API CSRF prevention is disabled. A digest of the displayed invoice/order consent text rejects stale or changed forms in addition to the native nonce and consent version. The digest is a change detector, not an authentication credential. Browser-supplied gateway/environment/customer/amount fields cannot override saved configuration; ambiguous MolliePayments gateway instances fail closed. Invoice hash access alone is insufficient to grant automatic-payment consent.

The authenticated request invokes issue #7 Customer resolution with creation and provider verification enabled. Customer/profile/credential changes block reuse. The existing invoice lock and unique active-invoice reservation commit consent version/text/server timestamp, owner/gateway/environment, immutable first-payment request, Customer mapping/profile reference, order ID and period in the immutable request metadata, and idempotency key together before the payment POST. Identifiers already contained in the saved request are not copied to a separate onboarding table. The exact consent text includes the order number, title and period, with version `order-collection-v3` and a server-side timestamp. Existing v2 attempts retain their original text, version and timestamp for resume and verification. Old broad v1 evidence is retained and may still settle its verified payment, but cannot become order-scoped readiness; it requires manual review. No additional table or schema change is needed for the order association. Existing nullable attempt columns retain minimal consent and mandate-verification observations. Ordinary `oneoff` requests stay unchanged and never create Customers.

The first payment uses the native eligible invoice total and currency, with all existing exclusions for allocations, Add Funds and unsupported currencies. SDK `CreatePaymentRequest` receives `sequenceType: first` and the verified `customerId`. Callback URLs, 45-minute replay window, credential binding and lease protection reuse the normal checkout path. An unresolved creation must be reconciled, never replaced merely to unblock checkout.

Authenticated payment retrieval verifies sequence, Customer, profile, environment, invoice, amount/currency and immutable attempt metadata. Only paid with a paid timestamp enters the existing native financial transaction path. Invoice settlement and the attempt guard commit atomically and exactly once. Failed/canceled/expired release only the active slot; pending/authorized/open do not settle. A delayed pre-payment response cannot downgrade verified payment or onboarding state.

Mandate verification follows financial commit. A narrowly scoped CustomerService path reads the persisted, settled, consenting first attempt and verifies the saved Customer/profile using GETs with saved credentials. It never supplies a fabricated browser identity or permits Customer creation. The payment's own `mandateId` or exact authenticated `_links.mandate` association supplies the candidate; contradictory references require manual review. A stored ID alone, instrument identity, Customer match, creation time or unique list result cannot prove this relationship. Without an explicit association, verification remains `pending_mandate` until the seven-day recovery deadline, then requires `manual_review`. A later explicit association can still be verified through the owner action. See [the final corrections](PR18_FINAL_FIXES.md).

The candidate is fetched under its owning Customer and checked for resource/ID, Customer reference, environment, status and method. Eligible method mappings follow Mollie's [recurring guide](https://docs.mollie.com/docs/recurring-payments): card to card, PayPal to PayPal, and the documented bank-based first methods to SEPA Direct Debit. Unknown/new methods fail closed. The invoice-backed positive-amount flow does not implement BACS zero-value setup. SEPA Direct Debit must be enabled for bank-based mandates; PayPal availability depends on merchant configuration. [List methods](https://docs.mollie.com/reference/list-methods) with `sequenceType=first` and invoice amount/currency can inspect profile availability; Hosted Checkout handles method selection for the first request.

A valid mandate must also support merchant-initiated collection (`customer-not-present`). Explicit response scopes are checked when supplied; the [scope-filtered mandate list](https://docs.mollie.com/reference/list-mandates), starting at the exact candidate ID with limit one, must return that same valid mandate. The SDK v4.0.0 Mandate resource has no declared scopes property, but preserves extra response fields. If the provider cannot establish the association or scope unambiguously, the adapter preserves pending/manual review rather than guessing. [Get mandate](https://docs.mollie.com/reference/get-mandate) is authoritative for the fetched mandate; a paid payment alone is insufficient.

Onboarding states are `pending_payment`, `payment_failed`, `pending_mandate`, `mandate_invalid`, `manual_review` and `ready`. Readiness requires both recorded consent and a verified suitable valid mandate. It is a timestamped observation, not permission for this release to create recurring debits; future collection must reverify mandate and credential context. Only references, verified status/time and originating consent/payment association are retained; no bank/card details or provider exceptions are stored.

The page's **Check existing payment and mandate** POST (`client/molliepayments/onboarding_verify`) checks an already settled attempt using its original processed native transaction and fresh provider GETs, without creating a transaction. An unsettled payment still uses the existing native claimed financial recovery path. Neither path creates another payment or mandate. Webhook redelivery and the existing CLI `reconcile.php` command also reverify onboarding without a browser session. A mandate outage or pending/invalid/missing mandate does not undo paid invoice accounting. A worker lease fences late mandate observations; a competing check can finish first, so repeat the read-only check if it is still pending.

No recurring charges, Mollie Subscriptions, retry scheduler, revocation interface, refunds or chargebacks are added. Provider/browser validation evidence and remaining gaps are recorded separately in [VALIDATION.md](VALIDATION.md).


## Verified transaction invoice association

The native transaction `invoice` relation is distinct from the stored IPN `get.invoice_id`. `ServiceTransaction::create()` uses only the **top-level** `invoice_id` to populate it. A permissive creation path or historical callback may therefore retain the GET hint while having no native invoice link. The current `ipn.php` forwards top-level invoice IDs and rejects invalid values; the adapter does not treat the nested hint as authentication.

For an unprocessed native transaction, MolliePayments requires the existing host processing claim, its MolliePayments gateway and persisted attempt/payment identifiers. It rejects an existing different invoice and any supplied conflicting GET invoice hint. A missing GET invoice hint is acceptable: the immutable attempt, independently fetched provider payment and full payment metadata establish the association. Customer/profile/consent checks still apply to `first`. Only after successful provider verification does the adapter lock invoice, attempt and transaction in that order, refresh the transaction, and use the native `Transaction::setInvoice()` relation plus Doctrine flush to attach the existing attempt invoice. Gateway, owner, currency, current relation and native processing claim are rechecked under locks. No transaction claim, invoice, payment attempt or provider payment is created to repair the relation.

A bare form callback to the current public `ipn.php` without a top-level invoice ID is rejected by native transaction creation before this adapter runs. MolliePayments cannot repair a transaction that the host never creates; its own saved webhook URLs remain invoice-bound. Recovering a missing relation on an already created/claimed row is supported, but accepting unbound public callbacks requires a separate secure upstream contract.

The link and native accounting commit together for paid callbacks. Pending/open/authorized and failed/canceled/expired callbacks also receive the verified link, without financial entries. A failed financial transaction rolls the new link back with accounting. Existing correct links remain intact; processed rows are not relinked. Native claims, attempt settlement guards and duplicate-callback accounting remain authoritative.

Historical processed orphan rows require operator/upstream review. Even a zero amount or matching local attempt is insufficient authority to change processed history, and the native update contract freezes processed associations. Run this **read-only** inventory (up to 100 newest orphan rows):

```bash
php module/Molliepayments/bin/diagnose-transactions.php /absolute/path/to/FOSSBilling/src
```

It prints operational transaction IDs, status, a local candidate invoice when attempt/payment/gateway agree, and `provider_verified: false`. It prints no raw IPN, Customer details, provider responses or credentials. The candidate is a clue, not an authenticated repair instruction. Review provider state using the original credential/environment and native audit history. Unprocessed errors can be retried through normal permission-checked native processing, which acquires the claim and executes the verified path. Do not directly invoke the adapter to bypass a claim. Already processed rows need a supported, audited upstream association-correction procedure; do not update them with SQL or re-run financial settlement. No broad backfill is supplied.

## Timestamp storage and presentation

Module `created_at`, `updated_at`, `consent_accepted_at`, `mandate_verified_at` and `lease_until` values are integer Unix seconds. They represent absolute instants; PHP, database and display timezone offsets must never be added to them. Lease deadlines remain 180-second absolute instants and unresolved creation replay remains limited to 45 elapsed minutes. Consent/mandate timestamps record local acceptance/verification observations, not Mollie's original mandate signature or payment completion times.

FOSSBilling bootstrap sets PHP's default timezone from `i18n.timezone` (UTC fallback). Native invoice/transaction `DATETIME` values use that PHP timezone through native `DateTime`/Doctrine conventions. They do not include an offset in the raw SQL string; module epochs are intentionally a different database representation. A MariaDB session timezone does not rewrite integer epoch fields or native DATETIME literals supplied by PHP. Compare instants with explicit timezone conversion, not by visually comparing raw integers with formatted strings or `FROM_UNIXTIME()` under an unrelated database session timezone.

`bin/status.php` retains the original attempt epochs and adds corresponding `*_local` ISO-8601 fields using `Support\Timestamps` and the PHP timezone initialized by the host, including the actual DST offset. No second timezone setting or application clock is introduced. Historical timestamps are not rewritten. If a native timezone configuration is wrong, establish which historical DATETIME rows were written under which timezone before considering an audited upstream correction; ambiguous local DST times cannot be reconstructed safely from naive strings alone.

## Native reuse and timestamp persistence

The [native reuse audit](FOSSBILLING_NATIVE_REUSE_AUDIT.md) records exact upstream contracts and compatibility decisions. Native invoice-item retrieval uses `InvoiceItemRepository::findByInvoiceId()`. Native Transaction ORM timestamps use Core `TimestampTrait` lifecycle callbacks; the adapter does not assign a second update timestamp. Processed callbacks return without updating history.

Module attempt/customer timestamps use Doctrine DATETIME fields stored as UTC `Y-m-d H:i:s` strings, including creation/update, consent, mandate verification and lease expiry. An inactive lease has a null expiry. Repositories retain conditional DBAL writes because ORM lifecycle callbacks do not run on those updates. The small `Timestamps` helper formats UTC values and compares elapsed retry/lease deadlines without DST ambiguity. `Timestamps::present()` renders `Y-m-d H:i:s` in the PHP timezone initialized by Core from `i18n.timezone`; there is no module timezone setting. Native invoice/transaction timestamps remain owned by Core.

This development schema change deliberately has no migration or historical conversion. Recreate the disposable module database before using it with former integer-timestamp tables. Existing databases must not be upgraded in place by this change.


## Authorization page pricing and consent versions

The left-aligned client page extends the native layout and uses Bootstrap only. The company name comes from `System\Service::getCompany()['name']`; Twig escapes it in the introduction and consent. Payment-state feedback and the initially unchecked consent remain, with separate first-payment and one-time actions.

The current recurring price is a read-only composition of `Invoice\Service::resolveRenewalLine()` (including renewal price/quantity overrides), `ServiceInvoiceItem::getTotal()` and `Product\Service::getRenewalPromoAdjustments()`. It therefore uses native renewal discounts rather than subtracting a first-invoice discount or repeating its total. The displayed interval comes from the actual order's native `Period`, without monthly conversion. The recurring price is explicitly **excluding tax**; no future tax rate is projected. The first-payment amount is the existing invoice's native `getTotalWithTax()`, including its quantities, discounts and tax treatment. Actual future invoices remain authoritative and amounts may change. No invoice generation, reservation, promo redemption or financial persistence occurs during page reads.

New consent uses `order-collection-v3`, naming the company and the payment method selected during Mollie checkout. Its digest binds the company/order consent, interval, displayed recurring amount/currency and first-payment amount/currency, so stale forms must reload. Stored v2 evidence remains unchanged: existing payments compare against the exact v2 text for resume/recovery, while new submissions must use v3. Neither the version bump nor a page visit rewrites attempts, requests, acceptance timestamps or idempotency keys. Automatic collection remains disabled.


## Payment modes and post-cart consent

Native gateway `config[payment_mode]` controls new MolliePayments checkout requests: `both` (default), `one_time_only`, or `recurring_only`. The policy is enforced before Customer creation, in all ordinary/first-payment entry points, again under the invoice lock before reservation/reuse, and when resuming a payment. An incompatible saved mode blocks retries without clearing an active slot; reconciliation and authenticated settlement remain available regardless of mode. One-time-only bypasses the authorization page, while recurring-only requires an authenticated eligible owner and explicit consent; unsupported/mixed invoices and guests cannot fall back to one-time payment through this gateway. Native wallet/free-order completion and other gateways remain Core responsibilities.

The optional `consent_notice` and `cart_checkout` client APIs let a custom theme capture the current v3 consent before native cart completion and submit the resulting hash, version/digest and explicit acceptance afterwards. Both entry points share identity checks; writes share the existing session CSRF and consent validation. Core resolves the invoice hash and retains gateway selection; MolliePayments checks ownership, the unique saved MolliePayments gateway, mode, recurring eligibility and existing attempts. No URL flag, client mode/source/amount or arbitrary gateway ID grants authorization.

Consent meaning/version remains v3: actual renewal invoices of the identified order, through the selected checkout method. New immutable request metadata records the fixed server source `onboarding` or `cart_checkout`; exact consent text/version/timestamp and existing order identity remain on the attempt. No table/column or financial state machine change is introduced. Existing requests, including source-less v2/v3 records, are never rewritten by later callers. Full provider metadata verification protects the stored source along with the existing payment identity. All reservation, retry, mandate and accounting safeguards still apply. See [the complete theme contract and example](CUSTOM_CART_CHECKOUT.md).


## Mandate hardening and bounded recovery

A completed first payment does not guarantee a `mandateId` or mandate link. Readiness requires an explicit association from the authenticated Payment response on every successful verification. A previously stored ID alone cannot substitute for this evidence. Instrument details and Customer-level mandate lists cannot distinguish overlapping first payments with the same instrument; no discovery heuristic is used. Contradictory ID/link/Customer references or changes to a bound ID require review. A late explicit association can resolve pending/review state without another payment.

Transient API/network failures and Customer lease contention preserve a previous `ready` and its original verification timestamp. Explicit `invalid`/404/410 removes readiness, while identity/scope/configuration mismatches require review. No replacement is guessed for an existing bound ID. A pending bound mandate can become valid on GET-only re-verification; the `customer-not-present` scope check remains mandatory.

Core's `AfterAdminCronRunEvent` performs at most five **settled mandate checks or expirations** per run. It reads the original successfully processed native transaction, verifies its invoice/payment/gateway/amount/currency and current credential context, then fetches and validates the Payment through authenticated Mollie GETs. It never calls `createAndProcess()`, creates a transaction, changes balances/invoice accounting or dispatches payment events. Webhook settlement and explicit CLI financial reconciliation retain their existing paths.

Native `NamedLock` serializes cron batches; existing attempt/Customer leases and conditional writes fence verification. Pending attempts within the seven-day window have a five-minute cooldown, including failed provider reads. At or after seven days from attempt creation, a leased pending record becomes `manual_review`, without provider I/O or financial writes. The transition logs once and is excluded from subsequent batches. An active lease postpones processing until safely available. No new table or column is needed; `updated_at` supplies recovery backoff.

Operators should inspect the original attempt and provider context before requesting another owner verification. A late explicit payment/mandate relation can restore readiness; an absent or contradictory relation requires provider investigation, not an arbitrary mandate assignment. Do not clear active attempts, replay settlement for mandate-only recovery or create a replacement first payment merely to refresh status. See [PR18_FINAL_FIXES.md](PR18_FINAL_FIXES.md) for recovery steps, compatibility limits and validation results. Browser E2E was excluded from this correction round because of the known upstream CSRF issue; no Core/session workaround was added. Automatic recurring collection remains disabled.
